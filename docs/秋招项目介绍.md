# PetVerse · 智慧养宠社区平台

> 面向宠物爱好者的微服务社区平台，覆盖「虚拟宠物养成 + 真实宠物档案管理 + 社区社交 + 周边商城」四大业务域，并自研 AI 服务提供**多模态养宠顾问对话（图片 / 语音 / 视频）、跨会话长期记忆**、健康智能评估、评论摘要与个性化推荐能力。

## 项目介绍

本项目基于微服务架构的宠物社区项目，采用 **Java + Python 混合微服务**：Java 侧包含网关、用户、宠物、动态（宠域空间）、社交、点赞评论通知、商城共 7 个服务；AI 能力独立为 Python（FastAPI）服务，注册进 Nacos 后由 Spring Cloud Gateway 统一路由（`/api/ai/**`），与 Java 体系共享网关鉴权与服务发现。

用户端核心业务围绕宠物主人展开：虚拟宠物签到养成（经验/等级）、真实宠物身份证与健康档案、宠域空间动态（可见性/热度榜）、好友与私聊、商家入驻与到店自提商城。AI 服务基于 **LangGraph 状态图编排**，为全站提供多模态问答（拍照问诊、语音提问）、跨会话长期记忆、健康评估、口碑总结与个性化推荐。

## 技术栈

Spring Boot、Spring Cloud、MyBatis-Plus、MySQL、Redis、RocketMQ、Elasticsearch、PostgreSQL + pgvector、**LangChain / LangGraph（StateGraph 编排 + checkpoint 短期记忆 + Store 长期记忆）**、FastAPI、OpenAI 兼容 LLM / 视觉 / Embedding / 语音转写模型、阿里云 OSS（多模态附件直传，与 Java 服务共用同一个桶）。

## 项目亮点

1. **自研多模态养宠顾问对话链路（图片 / 语音 / 视频）**：附件直传阿里云 OSS（`oss2` SDK 经线程池代理，与 Java 侧共用同一套配置与同一个桶），对象 key 形如 `ai-chat/{userId}/{yyyyMMdd}/{uuid}.ext`（用户命名空间 + 日期分区）；图片直接以 OSS 公网 URL 作为 `image_url` 分片交给视觉模型**回源拉取**，请求体不携带图片内容。音频走 OpenAI 兼容 `/audio/transcriptions` 转写，转写文本并入**检索 query（最有检索价值的文本信号）与对话记忆**；视频无原生理解能力时降级为文字占位引导用户截帧。**跨服务商混搭**开箱即用（文本走 DeepSeek、视觉走百炼 qwen-vl，Key/BaseURL 缺省自动回落）。成本与记忆双重治理：图片分片**只在当前轮现算**，历史轮仅保留文字描述——checkpoint 记忆里永远不存图片，避免上下文 token 与记忆存储被图片撑爆。附件安全四道闸：MIME 主类型 + 扩展名双重判定、uuid4 对象名 + 正则白名单（防路径穿越 / 任意文件读取）、分类型大小限额（图 10M / 音 20M / 视频 50M、单轮 4 个）、**服务端读取附件字节只认对象 key 且必须落在本人命名空间**（不接受客户端传任意 URL 去抓取，防 SSRF 与跨用户读取）。

2. **基于 LangGraph runtime store 落地跨会话长期记忆**：官方 `PostgresStore` 持久化，与 checkpoint（会话级短期记忆）**同库不同表、生命周期解耦**——删除会话只清短期记忆，长期记忆跨会话留存；命名空间按「用户 / 宠物」两级隔离（petId 字符串化，规避雪花 ID 经 JSON 下发的精度丢失）。写入侧每轮 `done` 后由后台任务用 LLM 结构化输出做**增量抽取**（add / update / delete 操作列表，不阻塞响应），只沉淀长期有效信息（用户偏好、宠物习性、病史），一次性提问细节不入库；且把现有记忆清单交给 LLM 比对，重复或演进信息必须 `update` **复用原 key**，配合「单条 50 字 / 单轮 8 条操作 / 比对清单 20 条」三重截断，防止记忆无限膨胀与异常输出污染；被中断的轮次（不完整回复易误导）不参与抽取。读取侧 `recall_memory` 图节点按命名空间召回（默认 20 条）注入 System Prompt，并在人设中约束「与其他记忆或本轮表述冲突时以用户为准、不暴露记忆实现」。对外提供记忆查询 / 删除接口 + 前端记忆管理弹窗（按「我的偏好 / 各宠物记忆」分组、可单条删除），命名空间由服务端按 `X-User-Id` 拼接，猜 key 也无法越权删他人记忆。

3. **独立设计实现 AI 对话编排引擎**：基于 LangGraph StateGraph 将「意图识别 → 长期记忆召回 → RAG 检索 / Agent 工具调用 → Prompt 组装 → 流式生成」编排为条件路由状态图，闲聊类意图自动跳过检索与工具节点以降低延迟与 token 消耗，纯附件消息（无文字）直接归入知识咨询、不再让分类器猜意图；Agent 通过 6 个工具（宠物档案 / 订单 / 购物车 / 商品搜索 / 评论 / 热门动态）查询用户真实数据作答；命中急症意图（中毒、抽搐、尿闭等）时强制注入「就医提示」安全护栏，防止 AI 越界替代兽医诊断。

4. **实现高可用的 SSE 流式对话链路**：自定义 `meta → delta → done` 事件协议，采用生产者-消费者模型 + 15s 心跳注释行防止网关/代理掐断长连接；**双层并发闸**（全局信号量 20 路、3s 获取超时 + 单用户 2 路，防脚本刷满挤占他人）实现过载保护；**LLM 首帧静默重试**（未产出任何内容即失败时重建流重试一轮，用户无感知，已产出则不重试防重复）；前端配套连接重试（退避 1s/2s）+ 连接 / 流双看门狗（10s 挂起、25s 静默）+ 失败气泡一键重新生成。用户中途停止生成时问题与已产出的部分回复双路收尾——补写图状态记忆 + 条件写入消息表（会话已删则原子跳过），`asyncio.shield` 保证取消路径写入落地，避免内容丢失、记忆断裂与重复写入。

5. **基于 LangGraph 官方 checkpoint 实现可恢复的对话记忆**：图状态 messages 按「用户 + 会话」线程由官方 PostgresSaver 自动持久化到 PostgreSQL，跨轮自动恢复上下文；用户停止生成时通过 `aupdate_state` 把问题与已产出的部分回复（`interrupted` 标记）补写回图状态，被中断的轮次同样进入后续对话的记忆；针对流式写入与「删除会话」的竞态，用条件写入（会话表存在性检查）避免已删除历史被“复活”；在 Windows ProactorEventLoop 约束下用「官方同步引擎 + 线程池代理」实现跨平台一致（Linux 亦可直接运行）。

6. **基于 pgvector 的知识库语义检索**：OpenAI 兼容 Embedding + pgvector 余弦相似度检索（阈值过滤 + TopK 限制 + 带来源引用注入 Prompt，降低幻觉），内置疫苗/驱虫/喂养/常见病/行为训练五类知识语料，`RecursiveCharacterTextSplitter` 中文友好切分 + 幂等导入（以文件为唯一事实来源）；检索链路不可用时**明确失败、不做降级**——宁可直接报错，也不拿低质上下文诱导模型编造答案（只保留一条检索通路，避免"看似正常回答实则无依据"的静默降级）。

7. **解决跨大模型厂商的结构化输出兼容问题**：不同服务商对 `json_schema` / `tool_choice` 支持差异极大（如 DeepSeek 思考模型两者均不支持，导致四类结构化任务**静默降级**为规则逻辑、接口仍返回 200 难以察觉），实现 `json_schema → function_calling → json_mode` 三级自动探测降级 + 可用方式进程级缓存，支撑意图识别、健康评估、评论摘要、推荐重排、长期记忆抽取五个 LLM 结构化输出场景稳定运行。

8. **落地事件驱动的微服务基础设施**：基于 RocketMQ 解耦异步链路——动态/商品的 ES 索引异步同步（挂了自动重投）、订单超时延迟消息自动取消并回补库存、点赞计数异步落库 + 通知投递、商家审核通过后角色升级；Elasticsearch 故障时 60s 熔断窗口自动降级 MySQL 模糊查询保障可用性；网关统一 JWT 鉴权、剥离并重注入内部 `X-User-Id` 信任头，支撑 Java / Python 跨语言服务间的身份透传与越权防护。

## 附：面试可展开的细节索引

| 亮点 | 常见追问 | 回答要点 |
|---|---|---|
| 1 多模态 | 图片怎么给模型 | 附件直传 OSS、给公网 URL 由服务商回源拉取，请求体不携带图片内容（省带宽，也避免大 body 拖慢首帧） |
| 1 多模态 | 客户端能伪造附件地址让服务端去下载吗 | 不能：服务端只在音频转写时按对象 key 取文件，且校验 key 落在当前用户的命名空间；绝不按客户端给的 URL 发起请求（防 SSRF 与跨用户读取） |
| 1 多模态 | 语音 / 视频怎么处理 | 音频走 OpenAI 兼容转写，转写文本并入检索 query 与记忆；视频无原生能力时降级为占位提示引导截帧发图；视觉 / ASR 未配置时均降级为文字引导，绝不阻断对话 |
| 2 长期记忆 | 怎么防止记忆膨胀 / 自相矛盾 | 抽取时把现有记忆清单交给 LLM 比对，重复或演进信息必须 `update` 复用原 key；单条 50 字、单轮 8 条操作、比对清单 20 条三重截断；中断轮不抽取（不完整回复易误导） |
| 2 长期记忆 | 为什么不用 checkpoint 存长期记忆 | checkpoint 是「用户+会话」thread 级短期记忆、随会话删除；长期记忆要求跨会话且生命周期独立，故用官方 Store 单独命名空间，删除会话只清前者 |
| 2 长期记忆 | 记忆删除会不会被越权 | 命名空间（`用户 / 宠物`）由服务端按 `X-User-Id` 拼接，客户端只能传 key，猜 key 也只落在自己的命名空间内 |
| 3 编排引擎 | 为什么用 LangGraph 而不是直接调模型 | 手写链路难以表达条件路由与多节点；状态图节点职责单一、可观测，`stream_mode="messages"` 只透传生成节点的 token 增量 |
| 4 SSE | 为什么不用 WebSocket / 轮询 | 单向推送场景 SSE 更轻；EventSource 不支持 POST 故用 fetch + ReadableStream 手动解析 |
| 4 SSE | 长连接中途断了怎么办 | 前端双层看门狗（连接 10s 挂起 / 流 25s 静默）主动 abort 并提示，失败气泡一键重发；服务端 15s 心跳兜底网关 idle 超时；LLM 首帧失败静默重试一轮 |
| 5 记忆存储 | 为什么不直接用官方异步 saver | 服务跑在 Windows，psycopg 异步连接在 ProactorEventLoop 下不可用；保留官方存储引擎与建表迁移、仅补线程池代理层，Linux 上行为一致 |
| 6 RAG | 检索不准 / 检索挂了怎么办 | 阈值过滤 + TopK 限制 + 来源引用；链路不可用直接报错而不是降级成关键词检索——知识问答里"无依据却答得像真的"比明确失败更糟 |
| 7 结构化降级 | 怎么发现这个问题 | 推荐理由全是模板文案才暴露；接口 200 但内容是规则兜底，属于"静默降级"，必须靠结果内容巡检发现 |
| 8 事件驱动 | 消息丢失/重复怎么办 | 生产端 MqEventPublisher 抽象 + 消费端 MqDeduplicator 去重；ES 索引可由 DB 重建 |
