# PetVerse · 宠域 — 秋招项目介绍

> 本文面向秋招，用于简历项目描述与面试讲解，核心亮点以有序列表按含金量从高到低排列（AI、Java 混排，每条带 【AI】/【Java】 标记），末尾附「设计取舍与已知边界」供面试主动展开。功能级细节见 [AI模块功能说明.md](AI模块功能说明.md) 与 [后端开发规范.md](后端开发规范.md)。

## 一、一句话简介

PetVerse（宠域）是一个面向宠物爱好者的社区平台后端，覆盖虚拟宠物养成、真实宠物档案、宠域空间（社区动态）、好友与聊天、点赞评论通知、周边商城、AI 养宠问询七大业务域。采用 Java + Python 混合微服务架构：Spring Cloud Gateway 统一入口、JWT 鉴权后向 Java / Python 两侧透传用户身份，各服务独立数据库、Nacos 注册发现与配置、RocketMQ 驱动异步链路；AI 能力由独立的 Python（FastAPI + LangGraph）服务承载，是个人核心投入方向。

## 三、核心亮点（按含金量排序，AI / Java 混排）

1. 【AI】**设计会话级 + 跨会话双层记忆，让 AI 既记得本次对话、又记得用户与宠物的长期偏好。** 短期记忆用官方 checkpoint（`PostgresSaver`），图状态 `messages` 按 `thread_id = 用户:会话` 在每个超级步自动持久化、下轮自动恢复；长期记忆用官方 runtime store（`PostgresStore`），按用户级 / 宠物级命名空间隔离，每轮结束后由后台任务用 LLM 抽取「偏好 / 习性 / 病史」等长期有效信息，产出 `add/update/delete` 操作应用到 store。防抖靠 `update` 复用原 key 覆盖（LLM 能看到既有记忆清单，重复或演进的信息不重复堆积），一次性提问细节（如「今天体温 39 度正常吗」）不进记忆；抽取放在 SSE `done` 之后不阻塞响应。两类记忆同库不同表、生命周期解耦——删会话只删短期记忆，长期记忆跨会话保留。

2. 【AI】**定位并彻底修复「用户点停止生成后 AI 就失忆」的问题。** 中断发生在生成节点落盘之前，若不处理，这轮「问了什么 + 答了多少」会在后续对话里完全缺失。方案：在 `asyncio.shield` 保护下用 `aupdate_state(as_node="generate")` 把用户问题与已产出的部分回复（打 `interrupted` 标记）补写回图状态，PostgreSQL 侧 `save_turn_if_exists` 兜底（会话已删则原子跳过、不复活历史），且用户消息无条件落库（即使中止时零产出，首轮提问也不丢）。用 `shield` 是因为取消路径里的裸 `await` 可能被再次取消导致写入夭折。

3. 【AI】**把一轮对话拆成单一职责节点、按意图条件路由，各路上下文按需装配而非每轮全量执行。** 意图分 5 类（闲聊 / 知识 / 健康 / 急症 / 查数据），知识类才走 `pgvector` 检索、查数据类才起 Agent 工具、闲聊直接生成；最终 Prompt 由人设 + 宠物档案 + 长期记忆 + RAG 知识 + 工具数据 + 医疗护栏按非空拼装。图 `compile()` 一次、进程内缓存复用。取舍：显式状态图比手写 if-else 更易观测和扩展（加节点即加能力），代价是引入图状态管理复杂度——对有 RAG / 工具 / 记忆多路上下文的对话系统是值得的。

4. 【AI】**对话链路做成生产级韧性，目标是「短暂故障不显化为用户可见的错误」。** 两级并发闸：全局最多 20 路流式对话（信号量 + 3s 超时即返回过载），单用户最多 2 路（防脚本刷满全局闸挤占他人），额度计数走 Redis 共享（多实例生效、Lua 原子增减 + 300s TTL 兜底回收），Redis 挂了退化进程内计数。SSE 每 15s 发心跳注释行防代理断连；流在产出任何内容前失败（服务商抖动 / 429）自动重建流静默重试一轮、已产出内容后不重试避免重复输出；LLM 流先搬进队列做生产者-消费者解耦，消费端对「等下一个片段」超时心跳，而非直接对 async generator 用 `wait_for`（超时取消会破坏生成器状态）。存储层读写全面降级、建表失败带 30s 冷却重试、`psycopg_pool` 断线自愈，PG 恢复后无需重启服务。

5. 【Java】**用 Redis 缓冲 + 脏标记 + 定时增量落库重构点赞，把高频写聚合成低频批量写。** 点赞读写全走 Redis `Set`（`like:{type}:{targetId}` 存点赞用户），变更打脏标记（`like:dirty:{type}`）；定时任务每 30s `SPOP` 脏标记（单轮限 200 个），对每个对象做 Redis 集合与 `like_record` 的增量 diff（批量插入新增 / 批量物理删除取消 / `like_count` 快照 upsert，单条 SQL 批量 500 行），落库失败的对象放回脏标记下轮重试；列表页批量查询走 pipeline 一次往返取回整页计数与点赞状态，冷数据批量回填。取舍：用最终一致换吞吐，靠脏标记重试 + 计数绝对值覆盖保证收敛。

6. 【AI】**知识检索刻意「不降级」——宁可明确失败，也不让模型无依据地答得像真的。** RAG 用 pgvector + OpenAI 兼容 Embedding 做余弦相似度检索，带阈值过滤（丢弃低于 0.35 的低相关片段）与来源标注（回答可引用、降低幻觉）；Embedding 未配置或向量库不可用时直接抛 `RagUnavailable`，不退化为关键词检索、也不静默跳过。这是把产品可信度置于功能可用性之上的判断，而非技术偷懒。

7. 【Java】**订单链路同时防超卖、防死锁、防超时订单被支付。** 下单原子扣库存（`stock >= quantity` 条件 SQL 更新，`updated==0` 即库存不足），合并购买行后按商品 ID 升序扣减（并发下单各事务以相同顺序持锁，避免互相等待死锁）；超时取消用「延迟消息 + 支付/查询出口惰性取消」双保险（开源版 RocketMQ 延迟消息只支持固定档位且可能延迟或丢失），两条路径都用状态条件更新互斥、仅抢占成功的一方回补库存，保证不重复回补。

8. 【AI】**AI 结果做 Redis 热 + PostgreSQL 温两级缓存，扛住 Redis 故障与热点打穿。** 评论摘要 / 推荐读时 Redis 未命中回落 `ai_cache`、写时并行双写；单飞（同 key 并发只放行一次真实计算，其余等锁后取结果）防击穿，TTL 附加 0~10% 随机抖动防雪崩。取舍：温层命中不回填 Redis，避免「回填续期」让「推荐缓存 10 分钟自然过期重建」的 TTL 语义失真——温层定位是 Redis 缺失时仍可用，不是保温。

9. 【Java】**网关做防伪造的身份透传闭环，下游服务无需各自解析 JWT。** `AuthGlobalFilter` 先剥离客户端自带的 `X-User-Id/X-User-Role`（防伪造）、校验 JWT 后再把解析出的身份重新注入透传；下游 `UserContextInterceptor` 优先解析 JWT、无令牌时才回退解析内部头（仅供 Feign 直连），`afterCompletion` 清理 ThreadLocal 防线程池复用串号，`FeignUserContextConfig` 的 Feign 拦截器自动把身份头转发给下游。因外部伪造头已被网关剥离，内部头只可能来自服务内部、不可被客户端伪造；`/internal/**` 禁止从网关外部访问，管理端 / 商家端路径做角色校验。

10. 【AI】**Agent 工具按请求动态构建、闭包捕获 user_id，从设计上杜绝越权查询。** 命中查数据意图时起一个 ReAct Agent，模型自主决定调用哪些只读工具（我的宠物 / 我的订单 / 我的购物车 / 商品评论 / 热门动态 / 搜索商品）；`user_id<=0` 直接返回空工具集，工具返回内容截断到 2000 字符再入上下文，任何工具失败都降级为空、不影响对话主流程。

11. 【AI】**多模态附件直传 OSS，并在服务端读取时防 SSRF 与跨用户读取。** 图片走视觉模型 `image_url` 分片、音频走 OpenAI 兼容 `/audio/transcriptions` 转写、视频降级为文字占位提示；视觉 / ASR 未配置时优雅降级为「引导用户文字描述」，绝不阻断对话。安全点：服务端读附件字节（转写用）只按对象 key 取、且校验 key 落在本人命名空间（`ai-chat/{userId}/{日期}/{uuid}.ext`），绝不按客户端传来的 URL 去抓取，从根上规避 SSRF 与越权读取。

12. 【Java】**RocketMQ 消息「事务提交后发送」+ 消费端内存幂等，避免脏事件与重复消费。** `MqEventPublisher.publishAfterCommit` 用 Spring 事务同步器把发送挂到 `afterCommit`（避免「消息已发、本地事务回滚」的脏事件），无 Broker 时降级为记日志、发送失败只记日志不拖垮主流程；消费端内存 LRU `MqDeduplicator`（1 万条 / 12h TTL）按业务键去重，处理失败可 `release` 让 MQ 重试。异步链路覆盖发动态奖励宠物经验、ES 索引同步、订单超时取消、商家角色升级、点赞热度近实时同步、站内通知。

13. 【AI】**结构化输出跨服务商降级 + 统一 OpenAI 兼容接入，换服务商只改配置。** 意图识别 / 健康报告 / 评论摘要 / 推荐重排 / 记忆抽取都要 LLM 结构化输出，但 OpenAI 兼容服务商支持差异大（DeepSeek 思考模型既不支持 `json_schema` 也不支持 `tool_choice`），故按 `json_schema → function_calling → json_mode`（附显式 Schema 提示）顺序尝试并缓存首次成功方式；对话 / Embedding / 视觉 / ASR 全部 OpenAI 兼容，改 `base_url + model + key` 即可切换任意服务商；无 Key 时自动进 mock 模式（打字机模拟回复，编排逻辑照常跑），方便联调与演示。

14. 【Java】**把全文检索做成「MQ 异步建索引 + 只返 ID 回表 + 熔断降级」，动态与商品共用同一套：** 写入不在发布 / 改 / 删时同步双写 ES，而是事务提交后发 MQ 事件、由索引消费者以 ID 回表读最新数据刷索引（天然幂等、失败由 RocketMQ 重试，ES 抖动不拖慢主流程），点赞数等字段用局部更新避免整文档覆盖；ES 文档只冗余检索 / 过滤 / 排序所需字段（标题、正文经 IK 分词，及分类 / 作者 / 可见性 / 点赞数 / 时间），展示数据一律以 MySQL 为准——检索时 ES 只按相关度返回 ID，再回 MySQL 回表、复用原聚合逻辑并按 ES 返回顺序组装（相关度排序不被回表打乱）；查询用 `multi_match`（标题 / 商品名加权 `^3`、店铺名 `^2`）+ `fuzziness=AUTO` 容错别字 + `match_phrase` 加权，分类 / 作者 / 时间 / 可见性 / 状态以 filter 参与、不影响相关度打分；ES 异常即进入 60s 熔断窗口（窗口内不再访问 ES）、降级为 MySQL `LIKE`，也可用 `petverse.search.enabled=false` 全局关闭，索引缺失时按主键游标分批全量重建（每批 500）。

    ```
    优势
    1. 数据永远最新、以 MySQL 为单一事实来源。 ES 是异步同步的、天然滞后;回表 MySQL 拿到的一定是最新权威数据,不会出现"改了显示旧的、删了还在、计数不准"。也避免了 ES 与 MySQL 双写不一致时那种极难排查的脏数据问题。
    
    2. 有些展示数据根本存不进 ES——回表是省不掉的。 这是最硬的一条:一条动态要展示"当前登录用户有没有点赞",这是因人而异的,不是文档的固有属性,不可能预存进 ES;实时点赞数、评论数、作者最新昵称/头像同理。所以就算你想"全量放 ES 直接返回",这些字段也拿不到、仍要回表 + 跨服务聚合。既然回表免不了,就统一以 MySQL 为准。
    
    3. 避免字段冗余与跨服务双写的维护地狱。 全量进 ES 意味着作者改名、换头像、媒体增删、点赞、评论数……每个字段变化都要同步 ES;而作者在 user-service、点赞在 remark-service/Redis、媒体在 space_media,要跨域订阅所有变更事件,耦合度和管道复杂度爆炸。回表方案里 ES 只存最小检索字段集,冗余面小、同步简单。
    
    4. 降低 ES 写放大与集群成本。 ES 文档越大、更新越勤,段合并(segment merge)压力越大、磁盘/内存越吃紧。不存全量展示数据 → 文档小、更新少、ES 更省;高频变动的计数不进 ES,也避免热点文档被反复重写(就是前面聊的 likeCount 写放大问题)。
    
    5. 权限 / 可见性实时准确。 可见性、逻辑删除以 MySQL 为准,回表能拿到最新权限,避免 ES 滞后导致本该不可见的内容被搜到。
    
    6. 复用同一套渲染逻辑,降级路径行为一致。 ES 出 ID 回表后,和普通分页(MySQL 查实体)汇合到同一套 VO 组装 / 聚合代码;ES 挂掉降级 MySQL LIKE 时,两条路径同字段、同新鲜度。若 ES 直接返回文档,正常路径和降级路径的数据结构就对不齐了。
    
    7. mapping 演进 / 重建索引更轻。 索引只含检索字段,改 mapping、reindexAll 全量重建的成本小,不用搬迁大量展示数据。
    ```

    

15. 【AI】**面向 C 端养宠场景内置医疗安全护栏，且每张非对话图都有规则兜底。** 命中疾病 / 用药 / 急症意图时，最终 Prompt 强制附加「无法替代兽医诊断、务必尽快就医、勿自行用药」，健康评估也明确不做诊断、仅基于用户填写信息评估；健康 / 评论 / 推荐三张图在 LLM 失败或 mock 模式下分别降级为规则评分 / n-gram 词频关键词 / 启发式排序，保证能力永远有结果返回。

16. 【Java】**每日签到用 Redis BitMap 单命令完成原子判重 + 落位。** key `signin:{userId}:{yyyyMM}`、bit 偏移 = 当月第几天 - 1（单用户单月最多占 4 字节）；`SETBIT` 原子返回该 bit 原值（0 = 本次抢占成功、1 = 当天已签到），一条命令完成判重与落位，抢占成功时用 Lua 脚本刷新 40 天 TTL，`BITCOUNT` 统计当月签到天数；Redis 不可用时放行，由宠物档案的最近签到日期兜底判断。

17. 【AI】**一个踩坑后的跨平台工程决策：官方同步存储引擎 + 线程适配，而非硬上异步。** LangGraph 官方 `PostgresSaver/PostgresStore` 是同步实现，其异步版本依赖的 psycopg 异步连接在 Windows 默认 `ProactorEventLoop` 下不可用；取舍后保留官方同步存储引擎与建表迁移，只补一层 `asyncio.to_thread` 线程代理，全服务 PG 访问统一「同步池 + to_thread」这一套模式，既不阻塞事件循环又跨平台一致。

18. 【Java】**网关令牌桶限流，AI 流式接口单独用更小的桶。** 鉴权后按维度限流：已登录按用户 ID、无身份（登录 / 注册）按来源 IP；AI 对话是长连接流式接口，单独用更小的桶避免被单个用户占满；令牌桶在网关进程内维护、空闲桶自动清理、限流组件自身异常时直接放行（不因限流故障影响正常请求），超限返回 429 + `Retry-After`。

分层约定：`Controller`（只收 DTO、只返 `Result<VO>`）→ `Service`（业务逻辑 + DO/DTO/VO 转换）→ `Mapper`（只操作 DO），DO 不得越过 Service 暴露。跨服务同步调用用 OpenFeign（被调方接口放 `/internal/`，列表聚合一律走批量接口避免 N+1），异步用 RocketMQ（topic / tag 常量统一维护在 `MqTopics`）。所有表继承 `BaseEntity`（雪花 ID、创建 / 更新时间自动填充、`deleted` 逻辑删除全局生效）；雪花 ID 为 19 位 Long，由 Jackson 统一序列化为字符串，避免超过 JS Number 安全整数（2^53）被前端截断——这是个隐蔽但影响面大的坑。各 Java 服务业务配置统一下沉 Nacos 配置中心，密钥用 `${环境变量:占位}` 写法脱敏提交、运行时环境变量覆盖。

## 六、设计取舍与已知边界

设计取舍（来龙去脉）：

1. 为什么用 Java + Python 混合微服务，而不是纯 Java 接大模型？AI 生态（LangGraph / LangChain / pgvector 客户端）在 Python 侧成熟度远高于 Java，硬用 Java 反而要重造轮子。取舍是把 AI 拆成独立 Python 服务、经网关统一入口对外、用 `X-User-Id` 内部头打通两侧身份——既吃到 Python 生态红利，又保持 Java 主体架构一致性，代价是多一种语言栈与一套 Nacos 注册逻辑（Python 侧自建心跳保活）。

2. 为什么 AI 全部业务数据落 PostgreSQL 而非复用 MySQL？因为 RAG 需要 pgvector（MySQL 无原生向量检索），既然引入了 PG，索性把 AI 的会话 / 消息 / 记忆 / checkpoint / 健康报告 / 缓存温层全部收拢到同一个 `petverse_ai` 库，减少异构存储运维面；并提供一次性幂等的 MySQL → PG 迁移脚本（保留原会话 ID）。

3. 为什么消息要「事务提交后发送」、点赞要「Redis 缓冲再落库」、订单要「延迟消息 + 惰性取消双保险」？三者是同一类取舍：在「强一致但低吞吐 / 易出脏数据」与「最终一致但高吞吐 / 高可靠」之间，按场景选后者并用补偿机制兜底——事务后发送避免脏事件，脏标记重试 + 计数绝对值覆盖保证点赞收敛，状态条件更新互斥保证订单不被重复回补。

已知边界（面试可主动坦诚、体现工程判断）：

1. 暂无自动化测试模块，靠 `curl` 与前端联调手工验证正常与异常分支；这是当前最大的工程短板。
2. 部分状态是进程内的，多实例部署需外部化：网关令牌桶在进程内维护（按用户 / IP 分桶但桶不跨实例共享）、`MqDeduplicator` 内存去重适用于单实例消费、AI 全局并发闸是进程内信号量（单用户额度已用 Redis 跨实例共享）。
3. 长期记忆抽取依赖 LLM 输出质量，可能漏抽或误抽；已用 update 防抖 + 单条 50 字 / 单轮 8 条上限约束，但本质非确定性。
4. RAG 知识库是静态 `md` 全量幂等导入，无增量 / 实时更新机制；切换 Embedding 模型需重建向量集合（维度须与 `EMBEDDING_DIM` 一致）。
5. 商城仅支持到店自取（预留外卖配送扩展），支付为模拟支付（生成取货码核销，无真实支付网关对接）。
6. 各类降级窗口 / 冷却时间（ES 60s、建表 30s、并发闸 3s 等）是固定经验值，未做自适应调整。
