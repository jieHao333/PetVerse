# PetVerse（宠域）· 秋招项目介绍

> **一句话定位**：面向宠物爱好者的社区平台后端，覆盖「虚拟宠物养成 + 真实宠物档案 + 社区社交 + 周边商城 + AI 养宠问询」五大业务域；采用 **Java + Python 混合微服务**架构，由 Spring Cloud Gateway 统一入口，JWT 鉴权后向 Java / Python 两侧透传身份。

- **技术栈**：Java 21 / Spring Boot 3.4 / Spring Cloud 2024 / Spring Cloud Alibaba（Nacos）· MyBatis-Plus · MySQL 8 · Redis · RocketMQ · Elasticsearch 8 · 阿里云 OSS · Python 3.12 / FastAPI · LangChain / **LangGraph** · PostgreSQL + **pgvector**
- **服务规模**：1 个网关 + 6 个 Java 业务服务 + 1 个公共模块 + 1 个独立 AI 服务（Python），共 8 个可部署单元
- **个人工作**：独立完成后端全部设计编码——Java 侧公共能力下沉、网关鉴权与跨语言身份透传、RocketMQ 事件驱动链路；**Python AI 服务为个人核心投入方向**（LangGraph 编排、RAG、对话记忆、SSE 流式链路、长期记忆抽取）

## 核心亮点（按含金量从高到低）

1. **【AI】独立设计并落地 LangGraph 对话编排引擎，把「拼消息调模型」升级为显式状态图。**
   用 `StateGraph` 将对话链路编排为 `意图识别 →（条件路由）知识检索 / Agent 工具调用 → 长期记忆召回 → Prompt 组装 → 流式生成` 六个职责单一节点。意图分类用 LLM 结构化输出（5 类意图），失败自动降级关键词规则；纯附件消息直接归类为知识咨询，不浪费一次分类调用。命中 `medical_urgent` 时在最终 Prompt 中**强制注入就医安全护栏**，模型无法被诱导跳过。编排图进程内编译缓存（checkpoint + store 一次性注入），单次编排零重复构建开销。

2. **【AI】基于 LangGraph 官方 checkpoint 实现了「可恢复、可中断」的对话记忆，解决流式对话被中止即失忆的行业通病。**
   编译时注入 `PostgresSaver`，图状态 `messages` 通道（`add_messages` reducer）按 `thread_id = 用户:会话` 在**每个超级步自动持久化**，下一轮自动恢复上下文。关键难点在用户点「停止生成」的场景：中断发生在写入落盘之前，本轮问答会在后续对话中彻底缺失——为此在取消路径用 `asyncio.shield` 保护收尾写入，通过 `graph.aupdate_state(as_node="generate")` 把「问题 + 已产出的部分回复（标记 `interrupted`）」补写回图状态，使**被中断的轮次同样进入长期记忆**；同时用固定消息 id 保证 `add_messages` 按 id 覆盖去重，重复投递不产生重复消息。

3. **【AI】自建高可用 SSE 流式链路：自定义事件协议 + 三层韧性设计。**
   定义 `meta → delta * n → done`（异常时 `error` 收尾）事件协议，首帧 `meta` 回传 sessionId 供前端绑定自动新建的会话。韧性设计：① **15s 心跳**防网关/代理 idle 超时掐断，且用「生产者协程 + 队列」解耦 LLM 流与消费端，规避了对 async generator 直接 `wait_for` 超时会破坏生成器状态的陷阱；② **首帧前静默重试**——流在产出任何内容前失败（服务商抖动 / 429）自动重建重试一轮，用户无感知，已产出内容后绝不重试以免重复输出；③ **双级并发闸**——全局信号量 20 路（3s 拿不到即返回过载提示）+ 单用户 2 路，防止个别用户刷脚本挤占全局容量。

4. **【AI】实现跨会话长期记忆：runtime store 持久化 + 后台 LLM 结构化抽取。**
   基于 LangGraph 官方 `PostgresStore`，按 `用户 / 宠物` 两级命名空间隔离，与短期记忆（checkpoint）生命周期解耦——删除会话只清 checkpoint 与业务表，长期记忆保留。每轮对话正常结束后，后台任务把「本轮问答 + 现有记忆清单」交给 LLM 结构化输出 `add / update / delete` 操作列表并应用：**防抖靠 update 复用原 key**（而非重复 add），从机制上避免记忆条目无限膨胀；并用条数上限（8 条）、内容长度（50 字）双重截断，防止异常输出污染记忆。任务异步执行不阻塞 `done` 事件，全程静默降级。

5. **【AI】跨大模型厂商的结构化输出三级自动降级，规避「静默降级」。**
   OpenAI 兼容服务商对结构化输出支持差异极大（如 DeepSeek 思考模型既不支持 `json_schema` 也不支持 `tool_choice`）。实现 `json_schema → function_calling → json_mode` 三级探测链：逐级尝试并**缓存首次成功的方式**，后续调用零试错成本、失效时自动重新探测；`json_mode` 兜底时把 JSON Schema 显式写进 System Prompt（否则模型不知道字段结构），再由 Pydantic 在客户端强校验。该能力被意图识别、健康报告、评论摘要、推荐重排、记忆抽取五处复用。

6. **【AI】基于 pgvector 的语义 RAG，并做了「宁可明确失败，不可无依据作答」的产品级取舍。**
   知识语料按中文标点递归切分（chunk 280 / overlap 40），OpenAI 兼容 Embedding 向量化入 pgvector；检索侧做**余弦相似度阈值过滤**（`score = 1 - distance`，低于 0.35 的片段直接丢弃），检索结果带来源标注注入 Prompt 以降低幻觉。Embedding 未配置或向量库异常时抛 `RagUnavailable` 让知识类提问**明确报错，坚决不降级为关键词检索**——知识问答场景里「答得像真的但没有依据」比明确失败更糟。

7. **【AI】多模态咨询链路：图片走视觉模型、音频先转写、视频引导兜底，附件直传 OSS 不占服务带宽。**
   附件经独立上传接口直传阿里云 OSS（对象 key `ai-chat/{userId}/{日期}/{uuid}`），返回的公网 URL 由浏览器回放与视觉模型回源拉取共用；**图片仅当前轮以 `image_url` 分片发给视觉模型**，历史轮附件早已并入文字描述，避免重复发图烧 token。音频经 OpenAI 兼容 ASR 转写后回填 `transcript`，并优先作为意图识别与检索的文本信号；转写失败 / 视觉不可用时降级为明确的文字引导提示，绝不阻断对话。安全侧两道防护：服务端读取附件字节只认本人命名空间的对象 key（防跨用户读取），且**只按 key 取值、绝不按用户提交的 URL 抓取**（防 SSRF）。

8. **【Java】RocketMQ 事件驱动打通异步链路，用「本地事务 + 提交后发消息 + 消费端幂等」实现最终一致性。**
   消息发布器统一封装：`TransactionSynchronization.afterCommit` 保证**事务提交后才发消息**（杜绝「消息已发、事务回滚」的脏事件）、无 Broker 时 `ObjectProvider` 自动降级仅记日志、支持延迟消息固定档位。已落地四条链路：ES 索引同步、**订单超时延迟消息自动取消并回补库存**、点赞落库与通知二次转发、商家审核通过后用户角色自动升级。幂等由 `MqDeduplicator`（LRU 万级 + 12h TTL，消费失败主动 `release` 让 MQ 重试不被误拦）+ 消费端状态 CAS / 覆盖写共同保证。

9. **【Java】Java ↔ Python 跨语言身份透传的完整信任链，让 AI 服务零改造复用现有鉴权体系。**
   网关在 `HIGHEST_PRECEDENCE` 过滤器里**先剥离客户端自带的 `X-User-Id` / `X-User-Role`**（防伪造），再解析 JWT 并重新注入，同时对 `/api/shop/admin`、`/merchant` 做角色硬校验、直接拦截 `/internal/` 内部接口的外部访问；`petverse-common` 的 `UserContextInterceptor` 仅在无 JWT 时信任该内部头，Feign 调用自动透传。AI 服务只需读取 `X-User-Id` 即可直连各 Java 服务拉取真实数据，Python 侧完全无需实现一套鉴权。

10. **【Java】Redis 高并发点赞缓冲：把高频写从数据库转移到内存，再定时批量落库。**
    设计 `like:{type}:{id}` Set + `like:dirty:{type}` 脏标记：**只有 `SADD` 返回 1（真正新增）才标脏并发事件**，天然幂等；30s 定时任务用 `SPOP` 原子弹出脏集合、在全量内存集上做 Set diff 后事务化增删 + count upsert 落库，失败把元素回写脏标记下轮重试。冷启动回填时遵循「**有脏标记就不回填**」规则，避免异步快照覆盖掉尚未落库的新增点赞。

11. **【Java】Elasticsearch 全文检索 + 60s 熔断窗口自动降级 MySQL。**
    商品与动态双索引，DSL 用 `multiMatch`（标题权重 ×3 + `fuzziness AUTO` + `minimumShouldMatch 30%`）+ `matchPhrase` 加权，`filter` 子句走不打分缓存、可见性作为过滤条件进 DSL；检索只取 ID 再回表并在内存中**保序**，规避 ES 与 MySQL 数据不一致导致的字段陈旧。ES 异常后进入 60s 熔断窗口（`degradedUntil` 时间戳），期间直接走 MySQL `LIKE` 兜底，窗口结束自动重试源，无需人工介入。

12. **【Java】商城交易链路：原子扣减防超卖 + 状态 CAS 防重复回补。**
    下单用 `WHERE stock >= qty` 的条件更新原子扣减库存（并发下不会超卖），任一商品失败即抛业务异常回滚；支付超时由延迟消息触发取消，**取消前先做订单状态 CAS，成功者才回补库存**，从根本上杜绝「重复消费导致库存虚增」；支付接口同样以状态 CAS 与惰性超时取消互斥，查询出口也会惰性取消过期订单，保证用户看到的订单状态始终自洽。

13. **【AI】两级结果缓存：Redis 热层 + PostgreSQL `ai_cache` 温层，由门面统一读写。**
    评论摘要（TTL 6h）与个性化推荐（TTL 10min）读时先 Redis、未命中自动回落 PG 温层；写时两级并行双写。温层解决的是「Redis 实例故障 / 重启导致缓存全失效、请求透传重算（LLM + 外部服务查询）」的单点问题。有个刻意的反直觉设计：**温层命中后不回填 Redis**——避免「回填续期」让 TTL 语义失真（推荐缓存「10 分钟自然过期重建」的意图会被持续访问无限延长）。

14. **【AI】存储层韧性设计：跨平台适配 + 冷却重试 + 故障静默降级，PG 恢复后无需重启服务。**
    官方 `PostgresSaver` / `PostgresStore` 均为同步实现，而 psycopg 异步连接在 Windows 默认 `ProactorEventLoop` 下不可用——保留官方存储引擎与建表迁移、仅补一层 `asyncio.to_thread` 线程适配，跨平台一致。建表失败带 30s 冷却重试（PG 未就绪时不反复打请求），PG 恢复后自动重新启用记忆与持久化；读写策略分级：记忆读降级为「无历史」、写静默仅记日志（对话不中断），而会话增删这类「对话前提」的操作则明确抛错转统一业务报文，不允许静默失败。

15. **【Java】把点赞 / 评论 / 通知抽象为面向多业务域的通用服务。**
    以 `(targetType, targetId)` 泛化目标对象，一套点赞与评论能力同时服务动态、商品、评价等多个域，新增业务域只需加一个枚举值；通知链路统一收敛到单一 topic，由通知消费者按业务键去重入库，各业务方无需各自实现推送逻辑。

16. **【AI】另外三张业务编排图，覆盖非对话类 AI 能力。**
    健康评估（档案整理 → LLM 结构化报告 → 落库，缺字段主动提示补全，LLM 失败降级规则评分）；评论摘要（真实评论 → 情感/优缺点/关键词，LLM 失败降级为按评分均值 + 情感词 + n-gram 词频的规则摘要）；个性化推荐（`asyncio.gather` 并发拉取宠物/订单/购物车/评价/动态五路画像 → 关键词召回候选 → LLM 重排并生成推荐理由 → 写缓存）。推荐重排环节有**防幻觉约束**：只允许使用候选列表中真实出现过的 id，模型编造的 id 在合并阶段被直接过滤掉。

17. **【Java】公共能力下沉 + 雪花 ID 精度治理等工程化细节。**
    统一 `Result` 报文、全局异常处理、JWT 上下文（ThreadLocal + `afterCompletion` 清理防线程池串号）、MQ 发布/去重、OSS 上传封装（重试 + 双检锁客户端 + `@PreDestroy` 释放）全部下沉到 `petverse-common`，8 个服务依赖复用。针对 19 位雪花 ID 超过 JS `Number.MAX_SAFE_INTEGER` 导致前端尾数截断的问题，在 Jackson 层统一将 `Long` 序列化为字符串，从根上避免「按 ID 回溯实体全部失效」。

18. **【Java】宠域空间：三层可见性校验与近实时热度榜。**
    动态可见性（公开 / 好友 / 私密）在列表查询的 SQL 层做条件注入、详情接口再做一次归属校验，好友 ID 依赖的 Feign 调用失败时降级为空列表（最严格可见性）而非放行；热度榜不做实时聚合，而是用冗余列 + MQ 近实时更新 + 60s 定时兜底同步，用可接受的延迟换取查询性能。

## 设计取舍与已知边界（面试可主动讲的加分项）

- **知识检索不降级**：与 ES 的「熔断降级」策略相反，RAG 宁可报错也不退回关键词检索——不同链路的失败代价不同，降级策略应按业务语义分别设计。
- **跨服务最终一致性未引入本地消息表 / 事务消息**：当前用「事务提交后发送 + MQ 重试 + 消费端幂等」覆盖，发送失败仅记日志，存在极小丢事件窗口；若消息可靠性要求提高，会补本地消息表或 RocketMQ 事务消息。
- **服务内部信任头无 mTLS / 内部签名**：信任链依赖「网关剥离 + 服务端口不裸暴露」的网络前提；生产环境应叠加内网隔离或内部签名。
- **会话列表的未读数按会话逐个统计**：实现直观但在会话数多时是 N+1 查询，后续可改为聚合查询或 Redis 计数。
- **宠物签到经验发放未加分布式锁**：目前依赖业务低并发假设，后续可用唯一键或 Redis 锁保证幂等。
